## Release and source decisions

- `heapless` 0.9.3 addresses container panic-safety defects according to its
  [upstream changelog](https://github.com/rust-embedded/heapless/blob/main/CHANGELOG.md).
  The application uses `heapless::String` APIs unchanged; both target and host
  builds compile. The candidate host timing is recorded in
  `docs/performance/dependency-upgrades.md`.
- `cortex-m-rt` 0.7.6 adds optional Armv8-M MSPLIM initialization and startup
  fixes; 0.7.7 aligns `_stext` and changes the macro dependency to `syn` 3.
  These are listed in the [upstream changelog](https://github.com/rust-embedded/cortex-m/blob/master/cortex-m-rt/CHANGELOG.md)
  and confirmed in the downloaded 0.7.7 crate. No new optional startup
  feature was enabled. Stock and 300/75 release images compile on the pinned
  nightly. This does not establish correct startup on the physical RP2350.
- The [defmt 1.1.1 releases](https://github.com/knurling-rs/defmt/releases)
  add macro fixes and formatting support. The downloaded `defmt-rtt` 1.3.0
  source adds `drop-on-contention`, but its source warns that the mode
  identifies thread mode by `IPSR == 0`; on the two-core design, that is not
  a safe substitute for the HAL's multicore critical section. Keep its
  default critical-section mode during the dependency update and design
  nonblocking logging separately. Stock and 300/75 release images compile;
  physical RTT decoding and contention behavior remain untested. Strict
  Clippy initially stopped on baseline diagnostics; those were corrected in
  `d98a296`, and the current gate passes.
- Embassy's [RP examples manifest](https://github.com/embassy-rs/embassy/blob/main/examples/rp/Cargo.toml)
  confirms the published 0.10.0 / 0.8.0 / 0.5.1 family. The open
  [RP2350 timer-alarm issue #6528](https://github.com/embassy-rs/embassy/issues/6528)
  describes a plausible lost alarm in 0.10.0; the report has no linked fix.
  A firmware watchdog and hardware trace remain necessary. The default
  `defmt-rtt` critical section uses the HAL implementation, not a single-core
  interrupt-only lock. The downloaded `embassy-rp` 0.10.0
  `critical_section_impl.rs` reserves hardware spinlock 31, records the owning
  core, and disables local interrupts while held. This also meets the
  [cortex-m 0.7.8+ multicore requirement](https://github.com/rust-embedded/cortex-m/releases)
  for a genuine cross-core critical section after the transitive refresh to
  `cortex-m` 0.7.9.

## Lockfile and CI refresh

`cargo update` selected 51 newer compatible firmware packages and removed a
second `heapless` 0.8.0 copy. The host lockfile was already at its highest
compatible versions. The complete version audit found 46 firmware and 7 host package/version entries
behind a newer stable major or constrained minor release. The earlier three-row
inventory was incomplete. Exact parent requirements for every entry are in
[the complete constraint inventory](constraints-2026-10-11.md). Representative
constraints include:

| Package | Locked / available | Reason |
| --- | --- | --- |
| `az` | 1.2.1 / 1.3.0 | `embedded-graphics` 0.8.2 requires `~1.2.0` |
| `fixed` | 1.29.0 / 1.31.0 | 1.31.0 requires `az ^1.3`, conflicting with the graphics requirement |
| `generic-array` | 0.14.7 / 1.4.5 | `crypto-common` 0.1.7 requires `=0.14.7` through the PIO parser build chain |

Initial same-family constraints were checked with targeted `cargo update
--precise ... --dry-run` and `cargo tree --invert ...`. The complete inventory
adds exact locked-parent manifest requirements, including newer major versions.
The host graph has the same `az` constraint.
Forcing these with a patch would change upstream compatibility assumptions.

`proc-macro-error2` 2.0.1 is the newest release and triggers Rust's
[future-compatibility warning E0365](https://github.com/rust-lang/rust/issues/127909)
for a private `proc_macro` re-export. It still compiles on the pinned nightly;
this needs a future upstream release or a separately reviewed patch.

CI now uses [checkout 7.0.1](https://github.com/actions/checkout/releases),
[rust-cache 2.9.2](https://github.com/Swatinem/rust-cache/releases), and the
[rust-toolchain action's documented toolchain input](https://github.com/dtolnay/rust-toolchain)
to select the same `nightly-2026-10-10` as local builds. Dependabot now covers
the host crate. No GitHub runner execution has been observed locally.

The first refreshed firmware build reported a `.text` alignment warning:
`memory.x` overrode `_stext` at a four-byte-only address after the RP2350 boot
info. The new `cortex-m-rt` changelog assigns alignment responsibility to
overrides. Aligning `_stext` to 16 bytes removed the linker warning in the
stock compile; this still needs a physical boot test.

At the dependency-only checkpoint the host suite retained the audited 4 pass /
6 failures. Subsequent correctness fixes and architecture tests now pass; the
review does not attribute those fixes to dependency upgrades.

### Current application decisions

- Host channel tests use the same `embassy-sync` 0.8.0 and `critical-section`
  1.2.0 as the firmware, with the latter's host `std` backend only in tests.
- `embassy-rp` 0.10.0 remains the newest published release. Its RP2350 watchdog
  reset selection needs an application wrapper matching Raspberry Pi's SDK;
  see [progress recovery](../performance/progress-recovery.md). Its merged but
  unreleased [DMA abort fix #6002](https://github.com/embassy-rs/embassy/pull/6002)
  is not assumed present. Payload cancellation/chaining is not used.
- [Timer #6528](https://github.com/embassy-rs/embassy/issues/6528),
  [WFE idle #4818](https://github.com/embassy-rs/embassy/issues/4818),
  [priority bits #6695](https://github.com/embassy-rs/embassy/issues/6695) and
  [custom bootloader PRIMASK #4982](https://github.com/embassy-rs/embassy/issues/4982)
  remain device acceptance concerns. ROM boot is the supported starting path.
  Do not transplant proposed timer changes without a reproduced failure.
- Heapless open Deque/IndexMap reports do not match current String and Channel
  push/pop usage. Do not add `Deque::make_contiguous` without revisiting
  [#676](https://github.com/rust-embedded/heapless/issues/676).
- defmt-rtt may block if a probe selects blocking mode. Its optional
  `drop-on-contention` behavior cannot replace the multicore critical section.
  Nonblocking logging and probe-disconnect acceptance remain explicit work.
- `rustup update` completed for installed stable and nightly channels. Stable
  became 1.99.0; the latest nightly remained 2026-10-10, rustc
  `1.101.0-nightly (32dba69d6 2026-10-09)`. The reproducible dated nightly pin is
  used for all current verification.

### Later architecture dependencies and linker gate

`embassy-futures` 0.1.2 is now a direct dependency for cooperative raster
checkpoints. It was already in the locked firmware graph; no version changed.
The published release, exact `yield_now` implementation and its actual polling
contract were checked: wake and Pending once, then Ready. It does not promise
a minimum sleep or bound interrupt latency. See
[cooperative rendering](../performance/cooperative-rendering.md).

The extended runtime review found another integration effect of 0.7.7:
our FLASH section insertion moved the location counter used by default
`__sheap`/`_stack_end` definitions. Explicit RAM anchoring, linker assertions
and an ELF CI check now cover this, with a reproduced failing image and passing
stock/300 builds. See [memory layout](../performance/memory-layout.md).
## Buffered UART source correction

The released Embassy RP 0.10.0 needs additional UART corrections before use by
the vehicle owner. The application now patches only that crate to the complete
published source plus a documented three-file UART delta. See
[the fork review and reproducibility checks](../../firmware/vendor/README.md).
All other firmware lockfile versions stay unchanged. Host tests additionally use
the already-reviewed `embassy-hal-internal 0.5.0` ring implementation. The source
manifest, exact upstream commits, API compile guards and shared-function tests
make this patch independently reviewable; hardware timing remains unverified.

## Direct async IO interface for the UART owner

`embedded-io-async 0.7.0` is now an optional direct dependency for `longan-rx12`.
It was already resolved through embassy-rp; the lockfile adds only the package's
dependency edge. Three checks: the [latest release documentation](https://docs.rs/embedded-io-async/latest/embedded_io_async/)
still resolves to 0.7.0; the [upstream changelog](https://github.com/rust-embedded/embedded-hal/blob/master/embedded-io-async/CHANGELOG.md)
documents required flush, core::Error and defmt 1 changes; exact 0.7.0 trait
source and the vendored HAL implementation were read for cancellation/progress.
The adapter uses only read/write/flush, polls once, retains partial progress in
the shared pump and separately observes hardware BUSY. Its cancellation proof
depends on that reviewed HAL, not the generic trait contract. No dependency
version changed in this integration.
